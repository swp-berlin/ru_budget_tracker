# Speed Improvement Suggestions

Generated by Claude Opus 5 High

### Dev Measures

I profiled the running app against your real database. The numbers point at one dominant cause that isn't network-related at all.

What I measured
Treemap callback response: 5.33 MB of JSON, 4,415 nodes. Broken down by tree level:

Level	Nodes	Label text
0–2 (root → chapter → subchapter)	106	4 KB
3 (program elements)	4,309	1,016 KB (avg 241 chars each)
95% of the figure payload is the labels array, and 98% of those labels are level-3 nodes — which a treemap never displays until the user drills into a subchapter. Every page load ships and renders the entire program-element layer up front.

Gzip hides this on the wire (349 KB compressed), which is why compression helped but didn't fix it. The cost that remains is client-side: the browser parses 5.33 MB of JSON and Plotly computes layout for 4,415 tiles before anything paints.

Other measured costs:

plotly.min.js = 4.84 MB uncompressed (~1.3 MB gz). Correctly cached (max-age=31536000), so it's a first-visit cost only.
generate_figure = 1.4–1.8 s of server CPU per call, and it is not cached — only transform_treemap_data is. Every filter click pays it again.
Gunicorn runs 1 sync worker (Dockerfile:57 has no --workers), so that 1.7 s blocks every other user and every static file.
Fonts: 642 KB TTF with font-display: block (typography.css) — text stays invisible until it loads.
All /assets/* responses send Cache-Control: no-cache → a revalidation round-trip per file per visit.
Timeseries is already fast (0.02 s) — your cache-generation work paid off.
Recommendations, by leverage
1. Don't ship level 3 until it's needed. Send levels 0–2 on first render and fetch a subchapter's children on drill-down — you already have the click callback and store-treemap-node-map to hang this on. Payload goes from 5.33 MB to a few KB. This is by far the biggest win for both load and interaction.

If the drill-down plumbing is too invasive for now, truncating labels is a cheap partial fix. Measured, on the same figure:

Variant	Raw	Gzipped
As sent today	5.33 MB	349 KB
Labels truncated to 40 chars	0.53 MB	88 KB
A 241-character label cannot render inside a tile anyway.

2. Memoize generate_figure. lru_cache on the (budget_id, viewby, spending_type, unit, language) tuple removes 1.7 s from every repeat filter combination. The key space is small enough to prewarm at boot like you did for timeseries.

3. Raise the worker count. --workers 2-4 --preload — note gunicorn.conf.py's post_fork hook already assumes --preload, but the Dockerfile CMD never passes it, so that hook is currently doing nothing and you're on a single worker.

4. Fonts. Convert to WOFF2 (642 KB → ~150 KB), switch to font-display: swap, and add a <link rel="preload">. block is what makes the page look blank rather than slow.

5. Asset cache headers. One line in app.py, verified working:


app.server.config["SEND_FILE_MAX_AGE_DEFAULT"] = timedelta(days=365)
# menu.css: "no-cache" → "public, max-age=31536000"
Safe because Dash already appends ?m=<mtime> fingerprints.

6. Custom plotly.js bundle. You use treemap + bar/scatter; the full 4.84 MB bundle carries 3D, geo, mapbox, and finance traces you never touch. A custom build lands around 1.2 MB. Worth doing, but it's first-visit only — lower priority than the payload work.

One thing I couldn't check from this repo: whether Traefik's compression covers application/json POST responses (the _dash-update-component route), not just static files. Some proxy configs gzip static assets only. Worth confirming, since that's where the 5.33 MB flows.

Want me to implement any of these? Items 2, 3, 4, and 5 are small and independent; item 1 is the real fix and deserves its own branch.

### Production measurements
The treemap callback takes ~2.0 s server-side, every single time:


cold request   ttfb = 1.95 s    477 KB gzipped (5.66 MB uncompressed)
warm request   ttfb = 2.11 s    477 KB gzipped   ← identical, no caching
The warm request being no faster is direct proof that generate_figure isn't memoized — transform_treemap_data's cache is already warm from boot, so nearly all of that 2 s is figure construction plus serializing 4,415 nodes.

And you are running a single worker. Three simultaneous requests:


req3  ttfb = 2.00 s
req2  ttfb = 3.82 s
req1  ttfb = 5.74 s
Perfectly serialized in ~1.9 s steps. Three people opening the dashboard at once means the third waits six seconds — and that same worker is also serving the 1.5 MB plotly bundle. This is the finding that most changes my priority ordering.

First-load budget (gzipped over the wire):

Resource	Size	Cache
plotly.min.js	1,533 KB	✅ 1 year
Dash/React/dbc bundles	352 KB	✅ 1 year
Source Sans 3 TTF	245 KB	❌ no-cache
favicon + CSS + clientside JS	24 KB	❌ no-cache
treemap figure callback	466 KB	— (+2 s wait)
Total	~2.6 MB	~12 MB uncompressed to parse
Compression is fully working — including on the _dash-update-component JSON responses, which was my one open question. That's why the 5.66 MB figure only costs 466 KB on the wire. Nothing more to gain there.

What this changes
The wire is no longer your problem. The remaining time splits into: ~2 s of server CPU per interaction (serialized across all users), and ~12 MB of JSON + JS the browser has to parse and lay out before the treemap appears.

Revised priority:

--workers 4 --preload — one line in Dockerfile:57. Doesn't make a single load faster, but stops users queueing behind each other, and preload finally activates the post_fork hook in gunicorn.conf.py that's currently dead code. Cheapest meaningful fix.
Memoize generate_figure — turns that repeated 2.0 s into ~0. Prewarm the common combinations at boot as you already do for timeseries.
Stop shipping level 3 — 4,309 of 4,415 nodes are program elements nobody sees until they drill in. This is what makes the payload 5.66 MB and the render slow. Biggest win, biggest change.
Font → WOFF2 + font-display: swap — 245 KB → ~150 KB, and removes the invisible-text phase.
SEND_FILE_MAX_AGE_DEFAULT — kills the per-visit revalidation on fonts/CSS/JS (verified working locally).
Custom plotly.js bundle — 1,533 KB → ~400 KB, first visit only.
Items 1, 2, 4, and 5 are small, independent, and together should take the common case from ~2 s to well under half a second without touching your data model. Want me to do those four as one branch, and leave item 3 for a separate discussion?
